# {{repo_name}}

这是 {{parties}} 的协作仓库。人和 Agent 在这里对齐需求、已确认的约定、各方说明和接口文件。聊天记录只是草稿。代码仍在各自的产品仓库里写。

两个前端可以只在本仓库里互相约定，不必每次都拉上后端。谁参加一份需求，写在该需求的「参与方」里。

远程：`{{remote_url}}`

本地不要把本仓库克隆到别的路径。在每个产品仓库里：

```
.collab/identity.toml                 本机身份，不提交
.collab/{{checkout_dir}}/             本仓库的检出
```

产品仓库的 `.gitignore` 必须包含 `.collab/` 和 `.apifox/`，两处都不提交。进入检出之前先看身份文件。没有它，就按 `AGENTS.md` 的「身份」一节登记。

## 目录

| 路径 | 谁来写 | 里面是什么 |
|---|---|---|
| `AGENTS.md` | 初始化时写入，规则变更走合并请求 | Agent 和人每次协作都要遵守的步骤 |
| `collaborators.md` | 新协作者登记时追加 | 已占用的 `<角色>/<昵称>` |
| `parties/<id>/` | 这一方 | 给其他方看的说明。`domains/` 按业务域一篇 |
| `parties/<id>/README.md` | 这一方 | 这个 id 对应哪个代码仓库 |
| `reqs/` | 提出需求的人 | 需求文件和 `README.md` 索引。讨论不写在这里 |
| `api/<提供方>/` | 该提供方的角色 | 发布出来的接口文件，可以有多份 |

`parties/` 现有 {{parties}}。新的一端：加一个目录，在它的 README 写上代码仓库地址，并告诉已有协作者。

产品仓库里的实现文档（例如后端的功能说明）给该仓库自己的 Agent 看。其他方要依赖的行为，以本仓库的 `parties/` 和 `reqs/` 为准。

## 一份需求从提出到完成

1. 在 `reqs/` 新增 `<主题>-<三位序号>.md`，状态写 `讨论中`，索引加一行。同时开一个 Issue，贴上 `discussing` 和需要响应的 `to-*` 标签。
2. 问题、答复、接口变更申请都写在这个 Issue 的评论里，并回复到具体的那一条。评论以 `[角色/昵称]` 开头。
3. 不是原评论作者的人写下 `✅ 确认` 之后，用合并请求把该结论写入需求文件的「约定」。
4. 约定都落地后，状态改为 `已确认`。相关代码在产品仓库实现并合入后，改为 `已实现`，关闭 Issue。

派给自己的事：查看未关闭且带有自己角色标签的 Issue。GitLab 示例：

```bash
glab issue list -R {{gitlab_path}} --label to-fe
```

GitHub 示例：

```bash
gh issue list --repo {{github_path}} --label to-fe
```

把 `to-fe` 换成 `to-pm`、`to-be`、`to-qa` 或 `to-ops`。标签还用 `discussing` `confirmed` `done` `wontfix` 表示状态。

## 接口

调用方只读 `api/<提供方>/`。需要改接口时在对应 Issue 里提出，由提供方从自己的代码生成文件再提交到该目录。不要在前端仓库里维护第二份接口定义。

给人浏览或跑测试的工具不是本仓库的替代品。是否使用、用哪一个，写在 `api/README.md`。还没写的时候，由发布接口的一方询问用户后再记下来。
