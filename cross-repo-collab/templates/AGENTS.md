# 协作规则

本仓库是需求、已确认的约定、各方说明和接口文件的正本。聊天记录和各个产品仓库里的实现文档都不是跨方正本。代码仍在各自的产品仓库里改。

人和 Agent 使用同一套步骤。Agent 不能因为「只有自己看得到聊天」就把结论留在对话里。

## 身份

产品仓库里的 `.collab/identity.toml`：

```toml
id = "fe/cursor-k"
```

`id` 的格式是 `<角色>/<昵称>`。角色是 `pm` `be` `fe` `qa` `ops`。昵称区分这一台机器上的这一次 Agent 或这一个人，不按仓库取成同一个名字。后端仓库里的 Agent 用 `be`，前端仓库里的用 `fe`，除非用户指定了别的角色。

没有这个文件时：

1. 读 `collaborators.md`。
2. 选一个表里没有的 id，向用户说明并得到同意。
3. 在名册追加一行：身份、人还是 Agent、所属产品仓库、日期。
4. 把 TOML 写到产品仓库的 `.collab/identity.toml`。

此后每一条 Issue 评论、每一个合并请求说明，都用这个 id 署名。不要冒用别人的 id。

## 每次开工

在 `.collab/{{checkout_dir}}/` 中：

1. `git status`。有未提交改动就停，先处理，不要拉取覆盖。
2. `git pull`。
3. 列出未关闭、且带有 `to-<你的角色>` 标签的 Issue。命令见 README。
4. 打开这些 Issue，读尚未回复的、`@` 到你的 id 或 `@<角色>/*` 的评论，以及它们指向的 `reqs/*.md`。
5. 索引 `reqs/README.md` 里认领栏写着你的 id，或写着你的角色通配（如 `fe/*`）的行，也要看。通配表示这一角色还没有人认领。

不要为了找任务把 `parties/` 和全部 `reqs/` 读一遍。

## 需求怎么走

一篇需求是一对东西：`reqs/<主题>-<三位序号>.md` 加上一个 Issue。编号看 `reqs/` 里已有文件，取下一号。讨论只写在 Issue。Markdown 只留稳定内容。已有 `reqs/*.md` 时沿用它们的结构；还没有时写全下面列出的字段。

文件里要有：状态、发起人与日期、参与方、认领、涉及接口、Issue 编号、需求、约定、变更记录。

状态只用这些词：`草稿` → `讨论中` → `已确认` → `已实现` → `已废弃`。

参与方写 `parties/` 的 id，例如 `backend, user`。两个前端单独协作时可以是 `user, admin`，不必带上 `backend`。

认领写具体 id。还没有人接到时写 `be/*` 或 `fe/*`。某人认领：改成自己的 id，在 Issue 里说一声，并给该 Issue 打上自己角色的 `to-*` 标签。

新建需求时：

1. 从主分支开分支。
2. 写入需求文件，状态为 `讨论中`，并在 `reqs/README.md` 加一行索引。
3. 用 Issue 模板开单。正文与「需求」节一致。标签加上 `discussing`，以及每个需要表态的角色的 `to-*`。
4. 把 Issue 编号写回需求文件。
5. 开合并请求。推送和开请求之前向用户确认。

## 在 Issue 里说话

每条评论以 `[<id>]` 开头。需要对方动手时写 `@<id>` 或 `@<角色>/*`，并给 Issue 加上对方的 `to-*` 标签。对方处理完，去掉这个标签；若还要下一个人，再加上下一个 `to-*`。

回复时使用平台的「回复此评论」，让后来的人能看出是在答哪一句。不要另起一条不挂钩的评论来回答。

常用句式：

```
[fe/cursor-k] 问 @be/*：验证码错误时，微信 code 是否仍可使用？
[be/claude-01] 答：仍可使用。短信验证码先校验，错误码 2012。
[pm/kevin] ✅ 确认
[fe/cursor-k] 接口变更申请 @be/*：注册响应需要让前端知道这次是不是新用户。
[be/claude-01] 答：已写入 api/backend/openapi.yaml 的该接口响应。见合并请求。
```

`✅ 确认` 的人必须不是被确认那条评论的作者。确认的是行为，不是接口字段表。确认之后开分支，把这句话写进需求文件的「约定」和「变更记录」，需要的话同步 `parties/<id>/domains/` 里给其他方看的说明。全部待确认的点都写进「约定」之后，状态改为 `已确认`，Issue 标签改为 `confirmed`。

实现完成、产品仓库已合入后，把状态改为 `已实现`，Issue 标签改为 `done` 并关闭。放弃则写 `已废弃`，标签 `wontfix`。

## 接口文件

正本在 `api/<提供方>/`。一个提供方可以放多份文件，文件名由该方决定。其他方只读，按文件里的路径和字段编写调用，不在自己的仓库里另写一份「我认为的接口」。

只有提供方对应的角色可以改该目录。前端需要新字段或新行为时，在 Issue 里写「接口变更申请」，打 `to-be`（或该提供方的角色标签）。提供方在自己的代码仓库改接口定义，生成文件，再提交到本仓库的 `api/<提供方>/`，并在原评论下回复改了哪个文件。

约定节里写行为、错误和顺序。字段表以 `api/` 里的文件为准，不抄进需求文件。

对外浏览或测试见 `api/README.md`。那里还没写决定时，由发布接口的角色询问用户，不根据产品仓库里有没有某个配置文件来猜测。

## 提交

产品仓库的 `.gitignore` 写上 `.collab/` 和 `.apifox/`。身份、协作仓库检出、Apifox 的项目配置都留在本地。缺了这两行就补上，并向用户说明。它们若已经被跟踪，先得到用户同意，再用 `git rm -r --cached` 从索引移除，不删除工作区文件。

本仓库的主分支受保护。改文件走分支和合并请求，由人合并。推送、发表评论、创建 Issue 和合并请求之前向用户确认。

合并请求说明里写关联的 Issue。一次合并请求只做一件事：新建一份需求、写入一项约定，或更新一个提供方的接口文件。
